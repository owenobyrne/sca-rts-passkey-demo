    How this maps to the rules

    And three places where the commonly circulated code snippet is wrong.

    The three corrections

    1. userVerification: "discouraged" defeats SCA. PSD2 Article 4(30) requires two independent elements. A passkey assertion with only UP set evidences possession alone. The second element — inherence (biometric) or knowledge (device PIN) — is evidenced only by the UV flag, and you get that by asking for userVerification: "required" and then verifying the flag server-side. Asking politely is not enough; the flag is the evidence.

    2. There is no extensions.payment dictionary on navigator.credentials.get(). The real mechanism is Secure Payment Confirmation: a PaymentRequest with the secure-payment-confirmation method, whose response.details is a PublicKeyCredential. The browser — not the page — renders the amount and payee, and writes them into clientDataJSON as clientData.payment, where the server can verify them. At registration the credential opts in with extensions: { payment: { isPayment: true } } — but only where the browser exposes PaymentRequest at all, because the SPC specification has create() throw NotSupportedError on a user agent without SPC, which would block enrolment outright rather than merely disabling SPC. Enrolment then steps down through fewer options (no payment extension, then ES256 and RS256, then ES256 alone) until the browser accepts, and the audit log records which one it was.

    3. Hashing the transaction is only half of dynamic linking. A hash is one-way, so a challenge alone tells the server nothing on its return journey. The server must keep the authoritative transaction (and the nonce) alongside the challenge, then re-hash the transaction it is about to execute and require that it equals the challenge inside the signed clientDataJSON. Without that final comparison, an attacker changes the amount after authorisation and the signature still verifies. Try it in step 5.

    Article 5 — what “dynamically linked” actually demands

    RTS Article 5(1) requires that:

    • (a) the payer is made aware of the amount and the payee;
    • (b) the authentication code generated is specific to the amount and the payee agreed to;
    • (c) the code changes if the amount or the payee changes;
    • (d) any change to the amount or payee invalidates the code.

    In WebAuthn terms: (a) is the visual confirmation — the panel in step 4, or the browser’s own SPC dialog; (b) and (c) come from committing the transaction into the challenge; (d) comes from the server refusing to execute anything that does not re-hash to the signed challenge, plus single-use consumption of the challenge.

    Article 5(2) adds confidentiality, authenticity and integrity requirements for the amount and payee “throughout all phases of the authentication”, which is why the origin check and the crossOrigin check are not optional extras.

    Where passkeys get interesting under the RTS

    Synced passkeys and “possession”. A passkey with BE=1, BS=1 is backed up to the payer’s cloud account and present on several devices. Supervisors have accepted synced credentials, but the possession element is then a key protected by the payer’s platform account rather than by one device’s secure element. That belongs in your Article 2 transaction-monitoring model — this demo surfaces the flags for exactly that reason.

    Independence (Art. 9). The elements must be independent: breach of one must not compromise the other. On a passkey, possession is a key held in the authenticator’s secure hardware and inherence is verified locally by the platform, which is what makes the combination defensible — but the analysis depends on the device’s secure execution environment, not on WebAuthn alone.

    Attestation. This demo requests attestation: "none". A PSP that wants assurance about which authenticator model holds the key needs attestation and a metadata service to check it against, and must weigh that against privacy and enrolment friction.

    Relying-party identifier. Hosted on GitHub Pages the RP ID is the *.github.io subdomain, which works because github.io sits on the Public Suffix List. A real PSP scopes credentials to its own registrable domain and lives with the fact that RP ID cannot be changed later without re-enrolling every payer.

    What a real deployment needs that this does not have
    • A genuine server: challenge state, credential registry, ledger and every check in step 6 must run somewhere the payer cannot reach. Here they run in your tab.
    • Article 2 transaction monitoring, Article 3 auditing, and Article 19 fraud-rate calculation and reporting — the TRA exemption is earned by an audited fraud rate, not by a checkbox.
    • Account-recovery and passkey lifecycle flows, which are usually where the real risk sits.
    • Accessibility and fallback authentication for payers without a usable authenticator.
